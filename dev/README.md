# Стенд разработки (без терминала)

Весь сценарий киоска проходится на обычном ПК: вместо диспенсера — эмулятор, вместо SOAP — заглушка,
вместо боевой БД — LocalDB. В боевую сборку ничего из этого не попадает.

## Запуск

VS Code → «Запуск и отладка» → **«Стенд (без терминала)»**. Поднимается:

| Что | Где | Чем заменено |
|---|---|---|
| Бэкенд (Development) | http://localhost:5115 | SOAP — заглушка (`TerminalSoap:UseStub`), БД — LocalDB `DbTerminalBpDm` |
| Киоск (Vite) | http://127.0.0.1:3000 | — |
| Эмулятор диспенсера | http://localhost:8080 — панель управления | сервис на терминале |

Перед стартом бэкенда задача «Init dev DB» создаёт базу и таблицы в LocalDB
([db/init-dev-db.sql](db/init-dev-db.sql)) — повторный запуск ничего не удаляет.
Нужны SQL Server Express LocalDB и `sqlcmd` (ставятся с Visual Studio / SQL Server), Node через nvm и веб-камера.

## Как проходить сценарии

- **Номер документа** — «Начать» → «Ввести вручную». **ИИН со скана** — «Начать» → «Сканировать удостоверение»
  и показать веб-камере тестовую карту со страницы `/?idscan` (на экране телефона или распечатанную).
  Исход определяет последняя цифра (заглушка `StubTerminalSoapClient`; у тестовой карты она случайная):

  | Цифра | Сценарий |
  |---|---|
  | …0 | пропуск не найден |
  | …1 | без фото — сразу выдача карты |
  | …3 | тип 3 — фото с красной рамкой |
  | …5 | без фото, RFID «half success» — карта выдаётся, причина в TerminalError |
  | …7 | без фото, сбой RFID — карта должна остаться в аппарате |
  | …8 | сервис отказал в сохранении фото |
  | …9 | SOAP недоступен |
  | другие | обычный посетитель с фото |

- **Диспенсер** — на панели http://localhost:8080: статус карт (0/1/2), исход выдачи (успех, ошибка UID, HTTP 500,
  ответ дольше таймаута), «диспенсер недоступен». В журнале видно, выдана карта (`allow=true`) или осталась в аппарате.
- **Терминал с «неправильным счётчиком»** — добавить `127.0.0.1` и `::1` в `Terminal:WrongCardCounterIps`
  в `backend/TerminalApi/appsettings.Development.json`.

## Где смотреть результат

- Фото, которые «ушли» в SOAP: `backend/TerminalApi/stub-photos/` (рамка, ориентация).
- Журналы, как на бою: таблицы `SearchRequestInfo`, `PassCardVisitorInfoLog`, `TerminalError` в LocalDB
  (`(localdb)\MSSQLLocalDB`, база `DbTerminalBpDm`). Киоск на этом ПК бэкенд видит как `127.0.0.1` или `::1`.
- Лог бэкенда: `backend/TerminalApi/logs/`.

## Галерея экранов

http://127.0.0.1:3000/?gallery — все экраны на трёх языках и шпаргалка сценариев.
Прямая ссылка: `/?screen=success&lang=KK&ratio=4:3` (`screen`: welcome, choose, scan, manual, loading, notfound,
error, confirm, photo, giveCard, success, nocards, settings). Работает только в dev.

## Распознавание удостоверения

http://127.0.0.1:3000/?idscan — тестовая страница: читает ИИН удостоверения РК (образец 2021 года) с лицевой стороны
(с датой рождения для сверки) или из MRZ на обороте — с камеры, из файла или с «тестовой карты» (синтетической,
обе стороны, с выдуманными данными и корректными ИИН и MRZ), так что настоящие документы для проверки не нужны.
Показывает, что вырезано, сырой текст распознавания и время.
Страница есть и в боевой сборке: на терминале на ней выбирают камеру документа и рисуют рамку карты — настройки
запоминаются в этом браузере, по ним же сканирует киоск. Кадры никуда не отправляются. Вход на терминале: удержать
3 с «Терминал готов к работе» (на любом экране) или «Бюро пропусков» (на главной) → в настройке экрана кнопка
«Распознавание удостоверения»; обратно — ссылка «← к киоску».

В киоске: «Начать» → выбор «Сканировать удостоверение» / «Ввести вручную» (выбор есть, только если у браузера есть
камера; нет — сразу ручной ввод) → экран сканирования. Камера — выбранная на `?idscan` (не выбрана или пропала —
камера по умолчанию), правила те же, что на странице, ИИН принимается после двух одинаковых чтений подряд и уходит
в обычный поиск. Посетитель видит кадр с рамкой найденной карты, шаги «на стекле → ИИН прочитан → проверен» и сам ИИН;
через 10 с без результата — подсказка, через 30 с — «Не удалось» с «Попробовать снова» и «Ввести вручную».
Распознавание загружается заранее, пока посетитель на экране выбора; камера выключается, как только экран закрыт.
Сбой камеры или распознавания уходит в TerminalError (`idscan: …`, ScanDoc).

- Распознавание — tesseract.js (WASM) прямо в браузере. Воркер, ядро и модель (~11 МБ, скачивается одно из двух ядер)
  отдаёт наш же сервер по пути `/tesseract/` (плагин в `frontend/vite.config.ts`), CDN не нужен. Сервер, который будет
  раздавать сборку, должен отдавать и `.gz` (модель `tesseract/lang/eng.traineddata.gz`).
- Режимы: «Зона ИИН» — быстро, по рамке карты (зоны ИИН и даты лицевой стороны, зона MRZ оборота); «Вся карта» —
  весь текст карты, медленнее, зато без рамки и для любой стороны; «Авто» — сначала зоны, не нашлось — вся карта.
- «Искать карту на кадре» (по умолчанию включено): карта ищется на кадре сама — светлый прямоугольник с пропорциями
  ID-1 на фоне стола; зоны берутся от неё. Нарисованная руками рамка поиск выключает. Мелкая карта (ниже 250 px
  по высоте, как на веб-камере 640×480 издалека) — символы 6–10 px, распознавание на пределе: результат помечается,
  а ИИН с лицевой стороны принимается, только если его подтвердило второе прочтение с другой обработкой.
- «Угадывать сторону и положение» (по умолчанию включено): по картинке, без распознавания текста, за миллисекунды.
  Положение — по левому верху (штрихкод или шапка) и левой середине (фото или чип): у ровно стоящей карты они
  выражены сильнее, чем у перевёрнутой. Сторона — по трём строкам MRZ через всю карту внизу. Догадка задаёт порядок
  попыток: сначала угаданная сторона в угаданном положении, потом остальное — ошибка догадки стоит времени, а не ИИН.
  Перевёрнутую (180°) карту, а «стоймя» — и на 90/270°, страница ставит ровно сама; угадывает, только если в рамке
  карта (найдена, нарисована или кадр сам по пропорциям карта), а не весь снимок.
- ИИН принимается, только если сходятся контрольная цифра, код века и дата рождения; с камеры — после двух
  одинаковых чтений подряд. Лицевая сторона: напечатанная дата рождения должна совпасть с датой внутри ИИН.
  Оборот (MRZ, ICAO 9303, формат TD1): ИИН стоит в первой строке после номера документа; сверяются контрольные цифры
  номера и дат и общая контрольная цифра — она покрывает и 11-ю цифру ИИН, которую не видит контрольная цифра
  самого ИИН. Поэтому прочтение с оборота, проверенное целиком, — самое надёжное.

Тесты: `npm test` — логика ИИН, обработка картинки и геометрия зон, без браузера; `npm run e2e:idscan` — страница
в headless Chrome/Edge, в dev и в боевой сборке, с заблокированным CDN.

```
cd frontend
npm test
npm run e2e:idscan
```

Статистика по 50 случайным тестовым картам на каждую комбинацию стороны, режима и масштаба (порог — выбранный):

```
set IDSCAN_STRESS=50
npm run e2e:idscan
```

Свои фото (несколько — через `;`) — печатает, что прочитано и сырой текст распознавания
(с `IDSCAN_EXPECT=<ИИН>;<ИИН>…` ещё и сверяет):

```
set IDSCAN_IMAGE=C:\фото\лицевая.jpg;C:\фото\оборот.jpg
npm run e2e:idscan
```

Фото настоящих документов в репозиторий не кладём.

## Автотест

```
cd frontend
npm run e2e
```

Headless Chrome/Edge (путь можно задать в `CHROME_PATH`) с фейковой камерой, эмулятор диспенсера и мок бэкенда:
выдача и отказ RFID, отсчёт, ошибки диспенсера, сканирование удостоверения (тестовая карта вместо камеры), фото,
галерея, боевая сборка (курсор мыши на терминале скрыт, а по `localhost` — на самом сервере, где работают мышью
через RDP, — виден; терминалы открывают сайт по адресу сервера). Порты не пересекаются
со стендом — можно запускать, не останавливая его.

### Тот же автотест в Chrome 103 (как на терминалах с Windows 7)

Сборка Chromium 103.0.5060.0 для Windows — из официального архива снапшотов Chromium:
https://storage.googleapis.com/chromium-browser-snapshots/Win_x64/1002885/chrome-win.zip (~190 МБ).
Распаковать куда угодно вне проекта и запустить:

```
cd frontend
set CHROME_PATH=C:\путь\к\chrome-win\chrome.exe
npm run e2e
```

За корпоративным прокси curl из Git Bash качает только с ключом `--ssl-no-revoke`.

## Чего стенд не проверяет

Настоящий терминал: CORS реального сервиса диспенсера, его камеру, боевые SOAP и БД.
Для распознавания удостоверения — камеру документа под стеклом и скорость распознавания на процессоре терминала.
